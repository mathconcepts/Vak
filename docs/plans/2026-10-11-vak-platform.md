# CEO Plan: Vāk Platform
Generated by /plan-ceo-review on 2026-10-11

## Vision

**One line:** any prayer, chanted word by word, alone or together, prepared by a harness that any model can drive.

### 10x check
Today: one stotram, one recording, one private page, hours of manual alignment per prayer.
10x: a family opens one link during Navarathri, in their own script. Whoever leads plays; everyone else's screen follows the same word in gold, across cities, with no login. A new prayer becomes a verified, word-timed pack in 15 minutes or less from the desktop, with an accuracy report, whichever model is driving.

### What we are deliberately NOT building
A general-purpose agent harness or chat app. Goose (Linux Foundation AAIF), OpenCode and Claude Desktop already are that. Our harness value is the **domain pipeline and its verification gates**, exposed as MCP tools that any of those hosts can drive.

### The prayer pack (the contract between Studio and Reader)

```
packs/<id>/
  pack.json      { id, version, title, source{url, edition, proofread_by},
                   sections[{title, verses[[line,...]]}],
                   scripts: generated at load from Devanagari (no stored copies),
                   recordings[{id, title, credit, license, url|null,
                               times[line], words[line][word]=[start,end]|null,
                               reprise[], notInRecording[], judge{sampled, ok, pct, date}}] }
  audio/<rec>.mp3   only if license permits public hosting
```
- Versioned: Reader caches by `id@version` and refreshes whenever it differs from the host's `latest` (either direction, so rollbacks reach devices), so a re-aligned pack replaces the old one cleanly. That fixes today's "stale copy" problem.
- `license` drives what the host serves. With `private` (the D4 case), the Reader asks for the file from the device; a private recording is never uploaded to any host.

### Together mode (revised in eng review: no database, signed messages)

Leader–follower over a dumb relay. The relay stores nothing; trust comes from a signature, not a server.

```
 create room (leader device):
   key  = WebCrypto ECDSA P-256 keypair (non-extractable; IndexedDB copy for "resume leading" is best-effort only)
   room = base64url(SHA-256(publicKeyRaw))[0:22]          ← channel name AND fingerprint (~132 bits)
   link = https://<host>/#r-<room>                          (WhatsApp share sheet; QR in P1.5)

 relay: Supabase Realtime *broadcast only* on public channel "vak:<room>"
        (no tables, no auth, no RLS, no cron; anon key) · LocalRelay (BroadcastChannel) for tests + same-device

 envelope: {b:"<exact UTF-8 JSON string>", s:"<sig>"} · sign/verify the bytes of b as sent (WebCrypto ECDSA/SHA-256
           hashes internally; never re-serialize before verify)
 messages from leader (all signed; seq = sessionStartMs·1000 + counter, so a reload never goes backwards):
   hello  {seq, pub, pack:"lalita@3", rec:"bhaskara", at}           on reconnect + when a ping arrives from a new follower
   pos    {seq, line, word, t, playing, rate, at:<leader ms>}       on play/pause/seek/line change + every 5 s
   pongs  {seq, at, r:[[pingId, recvAt], …]}                         ONE batched reply per second for all pending pings
   ping   {id:<random 128-bit>}  (follower → leader, unsigned; 0–10 s random jitter on join, 3 samples, then 1 per 5 min)

 follower accepts a signed message only if SHA-256(pub) matches <room>, seq > lastSeq, and |at − estimated leader now| < 10 s
          (blocks replays to new joiners too); a pong counts only for a ping id it is still waiting on.
 clock:   5 ping/pong round trips on join, then 1 per 60 s; keep min-RTT sample →
          offset = leaderAt + rtt/2 − localNow   (performance.now() based; offset to the LEADER's clock; re-sync on visibilitychange)
 follower position = t + (localNow + offset − at)·rate · between pos messages it extrapolates locally

 state:  SOLO ──create──► LEADING ──end──► SOLO
          └──open link──► FOLLOWING ──no pos 30 s──► WAITING ("Waiting for the leader")
          WAITING ──"Lead from here" (after 2 min)──► LEADING on a NEW room (new key, new link to share)
          WAITING ──same key reconnects (leader back from background)──► FOLLOWING   (followers wait 2 min before offering "Lead from here")
 leader:  share the link BEFORE pressing play; on visibilitychange→visible: reconnect, hello + pos, re-sync. Presence: leader only.
 handover: not in P1 (needs a key-chain certificate); "Lead from here" makes a new room instead.
 audio:  followers text-only unless pack licence allows or the file is on the device; then own audio,
         playbackRate nudged ±3% to stay within 0.3 s · big-screen/nearby: text only on phones
```

Why this shape: forwarding the link lets people *watch*, never *drive*, because only the private key can sign. Nothing to expire, delete, or back up. Lock room = "New link" (new key; old link goes quiet).

### Vāk Studio as a harness (the five layers)

| Layer | In Vāk Studio |
|---|---|
| Tools | Small, single-purpose MCP tools with typed inputs/outputs (see diagram). No "do everything" tool. |
| Verification loops | `text.check` (verse numbering continuous, no stray Latin), `audio.align` confidence per line, `audio.judge` listens to 30 random line starts, `pack.preview` renders the Reader headless and screenshots |
| Context & memory | `manifest.json` per pack: source, decisions (e.g. "nyasa lines 4–8 not chanted"), judge history; run log JSONL. Any host model reads the same state, so switching models loses nothing. |
| Guardrails | Publish refused unless gates pass; human approval prompt with the judge report; licence check blocks public audio; tools only write inside `packs/` |
| Observability | Per-run JSONL (tool, inputs hash, duration, result, gate verdicts); `studio.report` summarises; packs carry their judge score so users see "verified 27/30" |

Model-agnostic by construction: the heavy lifting (MMS aligner, Whisper judge) is local and model-free. LLMs only orchestrate, and orchestration goes through MCP, which Claude Desktop, Goose and OpenCode all speak.

### Recite mode (voice)
- **Now:** voice-paced following (shipped; tested within ±1 line on the ashram recording).
- **P3:** follow against the pack's reference recording, using online DTW (dynamic time warping) on voice features, so it tracks your voice word by word without needing pauses. Tested by pitch-shifting and speeding up the reference to imitate a different voice. Fallback to pace-following when a pack has no reference recording.

No catch-all handlers: every catch names one of the above, logs it, and shows its message.

## Failure modes (inversion: how this fails)
1. **Content trust breaks.** One wrong verse in a public pack and families stop trusting it. Mitigation: text gate plus visible source and edition plus a "Report a mistake" link per line.
2. **Together mode drifts.** Followers are a line off and the shared experience feels broken. Mitigation: 5 s + event broadcasts with local extrapolation, rate nudging, measured p95 exit test.
3. **Elders can't join.** The link opens in WhatsApp's in-app browser and audio is blocked. Mitigation: a "Tap to join" screen (gives the audio permission tap), and a tested WhatsApp in-app browser path on Android and iOS.
4. **Studio becomes a hobby harness.** Time goes into model adapters instead of packs. Mitigation: no custom agent loop; MCP only; P3 multi-model test is the only model work.
5. **Recording rights.** Public audio without permission. Mitigation: D4, plus a licence field that blocks it in code.
6. **Free-tier limits.** Supabase Realtime concurrency or Render bandwidth during a Navarathri spike. Mitigation: audio served from the static host with caching; relay carries only small JSON; a usage alert at 70%.

## Security & privacy
- No accounts, no database. Rooms are ephemeral broadcast channels named by the leader's public-key fingerprint (~132 bits). Only messages signed by the leader's non-extractable private key move the highlight; replays rejected by seq. Anyone with the link can watch (by design) or spam the channel, but cannot drive it. Spam is dropped at the signature check; worst case the leader taps "New link". Nothing is stored server-side, so nothing expires or leaks.
- Presence shows first names typed by users (Realtime presence, in-memory only). Nothing else is collected. No analytics beyond aggregate counts.
- Studio runs locally; tools write only inside `packs/`. Publish approval is a local OS dialog or terminal y/N raised by the Studio process; no MCP tool argument can approve. Text from `text.fetch` is data, never instructions. Model keys (LiteLLM) and publish credentials come from OS keychain/env, never written to manifest.json, the JSONL log, or packs; logs hold input hashes with secrets redacted.
- Sankalpa (P2): storage undecided after "no database" (see unresolved). Anon key is public, so anyone with a link can drain the project-wide relay quota; mitigation is the usage alert, not secrecy.

## Observability
- Reader: no server counters in P1 (no database). Error names logged to the console and a local ring buffer the user can copy into WhatsApp for support.
- Relay: Supabase dashboard usage only (messages, peak connections); drift measured from device logs during tests.
- Studio: run JSONL plus `studio.report`; each pack shows its judge score and date.
- Alert: realtime usage over 70% of plan; publish of a pack with judge < 90% (should be impossible; alerts if it happens).

### 1. Architecture
| # | Issue | Decision |
|---|---|---|
| A1 | Leader authority needed a server (JWT/RLS) | **[EUREKA]** Room name = fingerprint of leader's public key. Followers verify ECDSA signatures and seq locally. Server-side trust isn't needed because the relay is untrusted by design. |
| A2 | Clock sync assumed server time | Ping/pong to the **leader**: 3 jittered samples on join, min-RTT, batched signed pongs. Offset is to the leader's clock. Residual error ≤ path asymmetry/2 (unavoidable). |
| A3 | Relay lock-in and testability | `Relay` interface `{join, send, on, presence, leave}` with two implementations: `SupabaseRelay` (broadcast + presence only) and `LocalRelay` (BroadcastChannel, for tests and same-device). |
| A4 | claude.ai artifact CSP will block the Realtime websocket | Together ships in the PWA build only. The artifact build sets flag `together=false` and keeps working exactly as today. |
| A5 | Runtime CDN would break offline and old iPads | Bundle the realtime client into the page at build time with esbuild `--target=safari11`. If it won't transpile, fall back to a raw Phoenix-protocol WebSocket client (~100 lines), behind the same `Relay` interface. |
| A6 | One `Pack.from(obj)` path | Use the same validator for inline (artifact) and fetched (PWA) packs. Refresh when cached `id@version` ≠ host `latest`. |
| A7 | Sankalpa (P2) needs shared counting, which conflicts with "no database" | Unresolved for P2 (see below). Not in P1. |
| A8 | Outside voice: handover broke late joiners; seq reset froze rooms; ping fan-out blew quota; iOS backgrounding stranded rooms | Handover cut from P1 · seq = sessionStart·1000+n plus 10 s freshness · batched pongs, jittered joins, leader-only presence · leader reconnect + 2 min follower grace |
| A9 | Supabase pauses idle free projects | Weekly keepalive (GitHub Action hitting the REST API) + `RelayPaused` → solo mode. **D2 (user): Supabase broadcast + weekly keepalive.** Relay stays behind the `Relay` interface, so moving to an own Cloudflare relay later is a one-file swap. |

- One `Together` module with its state diagram as an ASCII comment. A single transition function `Together.go(next)` is the only place state changes.
- DRY: followers reuse `Music`'s time→word mapping (`wordsFor`, `fillWords`). There is no second timing path.
- Errors are named constants (`ERR.RoomHijackAttempt` …) with one `report(err)` that toasts, counts and logs. No bare `catch{}` in new code.

### 4. Performance
- **Relay quota:** every broadcast is billed once per receiving socket. Free-tier caps to respect: ~100 msg/s throughput, 200 concurrent, presence 20 msg/s (confirm the monthly figure on the pricing page at build).
  - Corrected budget per 30-min puja with 50 people: pos ≈ 760 × 51 ≈ 39k, batched pongs ≈ 1 per 5 min per follower ≈ 15k, total ≈ 55k. Join storm stays under 100 msg/s thanks to 0–10 s jitter and batched replies.
  - At 1 Hz, a 30-min puja with 50 people ≈ 90k deliveries, or ~22 pujas a month.
  - At **5 s plus events** (≈ 760 sends × 50) ≈ 38k, or ~50 a month. Decision: 5 s plus events, with followers extrapolating in between. Alert at 70%.
- ECDSA verify is under 1 ms per message, at most one every 5 s. Negligible.
- Service-worker cache: app shell + pack text ≈ 200 KB. Audio is never SW-cached. Own files stay in IndexedDB as today.
- Follower extrapolation runs inside the existing animation loop. No new timers.
